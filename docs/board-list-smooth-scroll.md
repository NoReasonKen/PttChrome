Pref `enableBoardListSmoothScroll` (**default `true`**). Implemented in `src/js/board_list_session.js`
plus the pure parsing layer `src/js/board_list_parse.js`; rendering borrows the `.listBodyView`
viewport from `src/render/screen.js` (the same one article-list easy reading uses). **Read this document before touching these three files or the board-list branch of `term_view`.**

Background: `docs/easy-reading-list.md` (the article-list easy reading v5 contract and scrolling model),

## 1. Scope (CONFIRMED, decided by the caption plus the command hints)

The variant is decided by `class_bid`/`yank_flag`. The old version (03cdf5eb) relies on a ternary in the footer (`board.c:1279-1290`); in the new version
(upstream `main`, scheduled to go live on PTT1 on 10/18) the caption comes from `board.c#brdlist_caption` by `class_bid`, and the hints are generated by
`psb.c#vs_cmd_bar` from the command table (prio ≥ HIGH goes on the bottom row as ` (k)name`, ≤ NORM on row 1 as `[k]name`). Details in
`docs/pttbbs-screen-protocol.md` §11.10. Decided by `board_list_parse.js#boardListVariant`.

| Screen | How it is entered | Old fingerprint (footer) | New fingerprint | Engages? |
|---|---|---|---|---|
| 我的最愛 (favorites, including subfolders) | Main menu `F` → `class_bid=0` + `LIST_FAV()` | `(a)增加看板` | caption `我的最愛` + `(a)增加看板` / row 1 `[y]列出全部` | ✅ `fav` |
| Category board subcategory | Pick a category in 【分類看板】 → `class_bid>1` | `(m)加入/移出最愛` + `(s)進入已知板名` | caption `看板列表` | ✅ `class` |
| 熱門看板 (popular boards) | `TopBoards()` / the `BRD_TOP` group → `class_bid=-1` | `(m)加入/移出最愛` + `(y)只列最愛` | caption `看板列表` (**indistinguishable from a category subcategory**) | old ❌ `all` / new ✅ `class` (the owner's decision; the order is dynamic, so stitching pages may duplicate or miss boards) |
| 全部看板 (all boards) | `y` on favorites → `class_bid=0` + `LIST_BRD()` | Same as popular boards | caption **still** `我的最愛` + `(m)加入最愛` / row 1 `[y]只列最愛` | ❌ `all` (tens of thousands of rows; how evict feels is unverified) |
| 「新文章」 (new articles) mode | `c` on any board list | One of the above | One of the above | ❌ `newflag` (row 2 「總數」, total) |
| Category board **root** | Main menu `C` (`class_bid==1`) | No footer | caption `分類看板` | ❌ fingerprint does not match (row 0 is 【分類看板】) |

Preconditions: row 0 starts with `【看板列表】` (`src/js/screen_titles.js#rowHasTitle`, **accepting both the `【X】` and ` X ` shapes**, for reasons in
protocol §11.9) **and** the footer caption is a board list (`src/js/screen_captions.js#isBoardListFooter`) → whether row 2 is 「編號」 (number)
or 「總數」 (total) (`board.c:1338`; the screen itself tells newflag apart, so there is no need to intercept the `c` key) → variant → the cursor rests in the body on a row with a number.
In the old version, **`(y)只列最愛` must be checked before `(m)加入/移出最愛`**, since both start with `(m)`.

**The terminal is not limited to 24 rows**: the engage condition (`board_list_session._engageEligible`) only requires
`buf.rows >= 24` (the lower bound is the server's clamp, `mbbsd/term.c:55`). **Never hard-code `=== 24`**:
with the settings page's "fixed font size", the row count is derived from the window height, and a hard-coded value would make the whole feature silently stop working.
The whole pipeline's geometry is already derived from `buf.rows` (`_bodyRows() = rows - 4` = pttbbs's
`p_lines`), with no real dependence on 24. See `docs/terminal-size.md`.

⚠ **guest has no favorites**: `choose_board` starts with `if (!cuser.userlevel) LIST_BRD();`
(`board.c:1665`), so guest pressing `F` lands on all boards. Offline cassettes can only record a category subcategory.

### 2.1 ⚠ Navigation keys wrap (unlike read.c; load-bearing for the design)

`choose_board`'s switch wraps on purpose through fall-through (`board.c:1751-1840`; newui moved it to
`board.c#board_cmd_pgup/pgdn/up/down/home/end` with identical per-key semantics, CONFIRMED; it also adds `Ctrl-B`/`Ctrl-F` paging):

| Key | Behaviour |
|---|---|
| `PgUp`/`P`/`b` | `if (num) num -= p_lines;` otherwise **falls through to `KEY_END`**, so PgUp on the first item jumps to the end of the list |
| `PgDn`/`空白` (Space)/`N` | `num == brdnum-1` ? **`num = 0`** : `num += p_lines`, so PgDn on the last item wraps back to page 1 |
| `↑`/`p`/`k` | `if (num-- <= 0) num = brdnum-1` |
| `↓`/`n`/`j` | `if (++num < brdnum) break;` otherwise falls through to `num = 0` |
| `End`/`$` | `num = brdnum-1`; `Home`/**`0`** | `num = 0` |

**The local cursor is clamped, following web conventions, instead of copying the wrap** (the owner's decision, 2026-09-02). Guarded by
the `board_list_session.test.js` group "local navigation (cursor clamped…)".

### 2.2 Server-side mouse (newui)

`psb.c#cmd_dispatch_layers` handles the mouse only when `key == KEY_MOUSE` (the client sent an SGR report): the wheel moves
`base` by ±1 (**breaking page alignment**), and the left button = select plus Enter. This client only reports when `listRenderMode === 'native'`,
pref `mouseServerReport` is on and the host has enabled tracking (`pttchrome.jsx#_serverMouseReportable`,
`mouse_regions.js#resolveMouseGates`), so nothing is sent while easy reading is in control. A wheel during the native mirror (functionMode) may leave the
server's `base` misaligned: pages are merged by **absolute number**, and `boardListFetchVerdict` only looks at where the cursor landed, so correctness is unaffected;
only the number of new rows that leg fetches drops. **If reports are ever sent while in control, base misalignment must be handled first.**

## 3. Why fetching pages does **not** use PgUp/PgDn (the biggest difference from the article list)

Each prefetch of article-list easy reading is two legs, "anchor number jump → PgUp/PgDn". The board list uses **a single number-jump leg** instead:

- Numbers are absolute positions with aligned pages, so jumping to `buffer edge ± 1` makes the server align `head` to the page containing it.
- `search_num`'s clamping lets the same leg probe the edge: **jumping down by one and staying put means the end of the list**
  (`boardListFetchVerdict`), with no second leg and no handling of §2.1's wrap.
- One round-trip (the article list needs two when not chaining).

The cost: number-jump legs always use `fullRepaint` (appending `\f`). When the target is on the same page as the real cursor, PTT sends nothing,
and `term_buf` only starts the settle timer on activity (protocol §6, the same as every number-jump leg of `list_session`).

`_edgeUp` has a free source as well: `bufferEdgeNum(nums,-1) === 1` means the target would be 0, so the top edge is decided directly, with zero bytes.

## 4. Architecture

### 4.1 Two sessions, one flag, one queue

`buf.listRenderMode` (`native`|`buffer`|`frozen`) is **shared**: it is already the branch point for a dozen consumers
(mouse coordinate conversion, left button, wheel, cursor highlight, `term_buf.onMouse_move`…), and a second flag would mean
writing every consumer's check twice. The two kinds of screen are mutually exclusive, so sharing is safe.

But both sessions hang off `screenSettled`, and in **the same frame** one may engage while the other tears down
(entering a board: ListSession engages and BoardListSession tears down; leaving a board: the reverse). So there are two layers of ownership,
both in `src/js/list_render_owner.js`:

| Layer | Field/function | Rule |
|---|---|---|
| Screen | `buf.listRenderOwner` + `defineOwnedRenderMode` | Writing buffer/frozen = claiming ownership; writing native = **releasing only what it holds itself**; reading = `'native'` when someone else holds it |
| Queue | The command kind's `BRD_CMD_PREFIX` (`'brd-'`) | Each settle handler calls `queue.onSettle` only when the in-flight command is its own (the two sides' facts have different shapes, and a wrong call fails silently) |
| Teardown | `queue.flushKind('brd-')` | **Never** use `flush()`: flushing the whole queue would kill the prefetch the other side has just enqueued |

So **whichever listener runs first, the result is the same**. Guarded by `tests/unit/list_render_owner.test.js` and
the flushKind group in `command_queue.test.js`.

`App.activeListSession()` (`pttchrome.jsx`) is the **single source of truth** for "who is drawing the list now";
the seven dispatch points (keyboard / paste / IME / function keys / left button / wheel / scroll events / render branch) all go through it;
on the `term_view` side this converges in the module-level pure function `listOwnerOf(core)`.

**Construction order matters**: `boardListSession` comes **after** `listSession` (`pttchrome.jsx`),
so in the frame of entering a board, ListSession engages first and we tear down afterwards, and the teardown's `flushKind` does not hit it.

| Item | Location |
|---|---|
| Buffer | `buf.brdListLines` / `buf.brdListLineNums` (**separate** from `listLines`, otherwise the two cleanups trample each other) |
| Accumulation | `term_view.accumulateBoardListLines` (`_brdNumMap`, keyed by number, whole-row overwrite) |
| Window | `term_view.buildBoardListWindowLines` (3 header rows + the whole sequence + footer) |

| Page-fill shift | Shared top reserve (`screen.absorbListShift`, which does not write scrollTop during a fling; see `docs/easy-reading-list.md` "A pure shift does not write scrollTop"). The at-top criterion `_atTopEdge` = `_edgeUp` **or the buffer containing item 1**; when the top edge is confirmed on a path that does not redraw, `_syncReserveTarget` must run there and then, otherwise the reserve stays and the wheel can scroll into blank space. The reserve is capped at the buffer's first item number − 1 rows (`listReservePx`'s `rowsAbove`): anything beyond that can only be removed by writing scrollTop, which keeps being deferred while scrolling, and once item 1 arrives it is a blank area you can scroll into; with the cap, filling up to the top absorbs it exactly |

**enhance's `pageState` is pinned to 1 (MENU), without `listEasyReading`/`inListContext`**:
`computeAnnotations`' `PAGE_LIST` branch runs `parseListAuthor` plus the blacklist check on every row,
and a board row's "author column" (cols 17-28) falls on the tail of the board name plus its category; a false hit makes **the whole board disappear**.

so no function-key buttons are lost. The mouse's column rules read `buf.pageState` (still 2 on the board list), so they are unaffected.
Guarded by `tests/unit/board_list_render.test.js` (including a control case: "with pageState 2 by mistake, whole rows are hidden").

### 4.3 State machine (`transitionBoardListSession`, a pure reducer)

`idle` → `active` ⇄ `functionMode`; `active` → `opening`; `active` → `suspended` → `active`.

**`suspended` (inside a board)**: entering a board hands back screen ownership, but **keeps the buffer, scroll anchor and variant intact**, so leaving the board
picks up where it was (like `list_session`'s suspended, article-list easy reading's invariant N6). If leaving the board re-ran `seed`, the anchor would
become the top row of the server's landing page, and `head = (num / p_lines) * p_lines` is 20-row paging (board.c:1710-1716),
so a board the reader scrolled to the bottom of the viewport, entered and left would snap back to the middle of the screen.

**Alias guard (load-bearing)**: **different lists** of the same variant share the same number-space shape. Enter on a category board's folder row
(`NBRD_FOLDER`) recurses into another `choose_board`, with an identical footer variant (board.c:1279-1290
only looks at `IS_LISTING_FAV`/`IN_CLASS`). So resuming must pass **two** guards:

1. `_reset()` only when the open-board transaction lands in **a different number space** (`brdlist`/`brdlist-other`/`menu`);
   everything else (board entry screen, article list, prompt, unknown landing) gets `_suspend()`.
   **This guard is by exclusion and must not be written back as "suspend only when the landing is `article-list`"**:
   the landing frame of opening a board is usually **not** the article list but the board entry screen. `Read()` runs
   `more(<board>/notes)` plus `pressanykey()` before `i_read()` (ctx is classified as `'other'`), and only
   when `currbid != bnote_lastbid` (the second entry into the same board in one connection skips it), so a whitelist version of the guard would
   **work only sometimes**: a manual test that enters the board just visited would not show it.
2. The landing frame on leaving the board passes another content fingerprint, `landedSameList`: the **board name** of the landed row (`parseBoardListName`)
   must match the buffer's row with the same number, **and the whole page is scanned**: every row on the landing page that has a row with the same number
   in the buffer must have the same board name (numbers the buffer lacks are no evidence). Any contradicting row means `seed` (a full rebuild).
   The whole-page half is the load-bearing complement added once gate 1 was relaxed: recursion into a group board (`BRD_GROUPBOARD`) also passes through the board entry screen first
   (board.c:1992-1998 is likewise `more(notes)` plus `pressanykey()`), so it too goes through `suspended`,
   and it lands on row 1 (board.c:1985 `num = 0`); comparing only the cursor row, "row 1 happens to have the same name"
   would merge the two lists into one buffer (a silent error).

**Coming back from the live layer (#122, mobile page stack)**: when, on leaving a board, the board list is shown from its live layer (`articleGestures.showsLayerOf(PAGE.BOARD_LIST)`),
`_resumeShown` no longer merges PTT's landing page into the buffer: once `_keepShown` is on, `term_view.accumulateBoardListLines` skips numbers already in the buffer
(unread ˇ, popularity and row order all stay as they were when the reader left), and only numbers the buffer lacks take PTT's current data; the selection stays on the row opened, and the landing only updates
`_serverNum` (opening another board later is aligned by the existing cursor-sync leg). The only in-place update is the ˇ of the board just visited: while suspended, every article-list settle
records "was the newest article read" with the home dashboard's `newestArticleUnread`, and on return that row is changed with `term_view.editBoardListRow` plus
`board_list_parse.setBoardListRowUnread` (the board name must match; when it cannot tell, it leaves the row alone). `_resetBuffer` (refresh's seed,
rebuild, switching to native) and the A-class keys (`v`/`V`/`t`) turn `_keepShown` off, returning to PTT as the source of truth. Without a live layer (desktop, beyond the live-layer bound, handoff timeout)
it merges as before. Guarded by the #122 group in `mobile_stack_board_reveal.offline.spec.js` (rewriting PTT's replies to simulate the list changing while inside a board).
When a board on the landing page with the same number and board name has a different unread ˇ from the buffer's (the board just visited excepted, since it follows the reader's own reading),
「有新文章」 ("new articles") flashes once through `NavigationStack.noticeNewContent` ([#128](https://github.com/NoReasonKen/PttChrome/issues/128);
it only looks at the landing frame PTT sends anyway, without sending keys; once per kept page, and after `_keepShown` turns off it counts as a new page).

`parseBoardListName` **does not use fixed columns**: the unread mark `unread[1]` is the full-width 「ˇ」 (board.c:1343),
which `rowToText` collapses into **one** character, so the board name's string index shifts by one between read and unread; it takes "the first ASCII identifier after the number"
instead. Guarded by the `parseBoardListName` group in `board_list_parse.test.js` and
`board_list_session.test.js` "enter board → leave board: buffer and scroll anchor kept across screens".

#### Background fill must go **both ways** (measured live, 2026-09-03)

`choose_board`'s `num` is static, so old PTT remembers where the reader last left, and **entry often lands right on the last page**
(newui always enters on row 1, see §2; but entering and leaving a board still lands anywhere, so both directions are still needed).
Filling only downwards hits the end of the list in one leg (`search_num` clamping), and background fill ends there: measured
`buffered=4`, a 20-row viewport, and the whole list above waiting until the reader presses ↑ themselves.
So `_maybeFill` is "down first, then up once the bottom edge is reached", and **fills unconditionally while the viewport is not yet full**
(that is not prefetching; this page itself cannot be drawn full); after `_enqueueFetch` decides edge, it must call
`_maybeFill` again to switch direction. Regression guards in `board_list_session.test.js`.

### 4.4 Transactions

| Transaction | Sequence | expect |
|---|---|---|
| Fetch page `brd-fetch-up/down` | `<base±1>\r` + `\f` | Rests in the body on a numbered row → `boardListFetchVerdict` decides edge |
| End `brd-jump-end` | Native `ESC[4~` + `^L` | Rests in the body with curX≤1 (board.c:1830 `KEY_END`/`$` → `num = brdnum-1`, CONFIRMED) |
| Home `brd-jump-home` | Native `ESC[1~` + `^L` | cursorNum === 1 (board.c:1768 `KEY_HOME`/`0` → `num = 0`) |
| Number jump `brd-jump-number` | `<n>\r` + `\f` | Rests in the body → `rebuild` (the landing may be far from the buffer) |
| Cursor sync `brd-*-sync-jump` | `<sel>\r` + `\f` | `cursorNum === sel ∧ same variant ∧ no board name on the page contradicts the buffer` (`_listContradicts`; in a different list the same number is another board, and Enter or ← follows right after) |
| Enter board `brd-open-board` | `\r` | **Any settle**; onDone → `_reset()` only when the landing is another list or menu (`brdlist`/`brdlist-other`/`menu`), otherwise (board entry screen / article list / unknown) `_suspend()` (buffer kept) |
| Back up a level `brd-leave` | `\x1b[D` | Same as above |
| passthrough `brd-native-key/paste/input` | The original key / Big5 bytes + `\f` | Same as above (the screen is already the native mirror) |
| A-class keys `brd-native-inplace` | `t`/`v`/`V` + `\f` (with `brd-inplace-sync-jump` first when needed) | `brd.parked ∧ cursorNum≠null ∧ same variant` → `_resumeInPlace` (adopts the landing, **anchor unchanged**); landing not in the buffer → `rebuild` |

"Entering a board and backing up a level always use `expect: () => true` plus teardown in onDone" on purpose: there are three kinds of landing
(article list / another board list / main menu or category root), and enumerating them in expect is far more fragile than "tear down, then let
the reducer of **the same settle** decide again from the content". After teardown the state returns to `idle`, and
the `inFlightKind` that `_settleEvent` reads is already null, so a board list is re-seeded on the spot,
and an article list is taken over by ListSession (whose handler already ran in the same round). For opening a board,
the "teardown" is `_suspend()` (buffer kept) rather than `_reset()`; nothing else changes.

**Known gap (not done)**: `suspended` only covers "enter board → leave board". **Entering a folder or group board and then backing up to
the list above** still re-runs `seed`, so the upper list's view is pinned again by the server's page. Fixing it would mean storing a stack of
upper-list buffers and anchors (parent and child share a variant and the same number-space shape, so ownership and the alias guards would all need rewriting);
deliberately left out of this round.

### 4.5 Keyboard whitelist (the enumeration is the contract)

Synonym keys follow `board.c:1751-1840`, **differing from read.c in two places**: PgUp has an extra `b`, and `0` is Home;
leaving is `←`/`q`/`e` (`e` leaves in both old and new board.c; before 2026-09-25 it was misclassified as passthrough). Opening is `Enter`/`→`/`r`/`l`. `1-9` collect a number jump in a local overlay.
**A-class keys (in-place redraw, 2026-09-03) = `t`/`v`/`V`**: `t` is `fav_tag`/admtag falling through to
`KEY_DOWN` (the cursor moves down one row), and `v`/`V` are `brc_toggle_all_read` → `show_brdlist(head,0,newflag)`, redrawing in place
(board.c:1802/1871). None of the three opens a prompt or changes the number space, so they go through a **frozen transaction** (`native-inplace`),
with native never visible. **`*` (tag all) is deliberately not in this group**: it flips the tag marks of the whole list at once, and other pages in the buffer would keep
stale marks, so it is passthrough (switching to native and rebuilding fully on return).
Ctrl combinations, Alt-remapped keys (Alt+R/T/W/V = `^R/^T/^W/^V`) and everything else → passthrough (**with a numbered selection and the real cursor
lagging behind, `native-sync-jump` first**, then switching to the native mirror and sending the key on the reader's behalf). Before 2026-09-13 these Ctrl/Alt classes were kept out of the sequence and so skipped
the sync leg, while board.c has a whole set of keys that act on the real cursor (`:1890 Ctrl-S`, `:2044 Ctrl-T`, `:1731 Ctrl-W`); the root cause and the rule are in
`docs/easy-reading-list.md` invariant 12. Once the operation completes and the screen has been quiet for 250ms, the **idle probe**
re-engages automatically (pref `enableListNativeAutoResume`, on by default; off = stay in native until entering a board or backing up a level).
The probe's three conditions and clock sources are exactly the same as the article list's; see the "Idle probe" section of `docs/easy-reading-list.md`.
Keys that cannot send a byte (F1/CapsLock…) → `ignore`, the criterion being `keyEventToBytes(e) == null` itself.

## 5. Invariants

- **I1 Ownership**: the screen, queue and teardown layers must all be owner-aware (§4.1). New dispatch points always go through
  `App.activeListSession()`; never read `buf.listRenderMode` yourself and guess who it is.
- **I2 A single line to the server**: share `App.commandQueue`, never build your own; commands always carry the `brd-` prefix.
- **I3 wrap-aware**: a clamped local cursor ≠ wrap can be ignored. **If pages are ever fetched with PgUp/PgDn again**,
  edge detection must be rewritten (§2.1): a landing that moves far in the opposite direction means edge, and **that landing is discarded**.
- **I4 newflag**: both lines of defence are required: the fingerprint layer checks whether row 2 is 「編號」 or 「總數」;
  the `c` key is already on the passthrough list (the buffer is void after switching to native).
- **I5 Zero-response Enter**: on separator lines (`NBRD_LINE`) and forbidden or hidden board rows, PTT replies with zero bytes,
  so **they must be blocked locally** (`isBoardListSeparatorRow` / `isBoardListBlockedRow`);
  sending would only freeze the screen until the timeout.
- **I5b Two kinds of hold** (as in `docs/easy-reading-list.md` N1): `beginExternalNavigation()` (AID jumps /
  long comments) writes `'external'`, **never released automatically**; non-whitelisted keys and self-healing degradation write `'passthrough'`, the only one the idle probe acts on.
- **I5c A-class frozen transactions must not move the scroll anchor** (as N6): `_resumeInPlace` only adopts the landing plus reveal,
  and does not go through `_adoptLanding` (which would reset `_topNum` to the native screen's top row, so the view would jump away instantly).
- **I6 Out of scope means back to native**: every settle reruns the fingerprint, and once it is no longer `fav`/`class`,
  it switches to the native mirror or tears down; **it must not keep drawing from the old buffer** (the number space has changed).
- **I7 Golden snapshots**: changes to `render/screen.js` or row output must run `render_dom_equivalence.test.js`.
- **I8 `view.conn`**: data always goes out through the queue or `view._send()`; `this.view.conn.send(...)` is forbidden.

Two hard rules when recording scenario cassettes (`record:scenarios`):
1. Letter keys on the main menu only **move the cursor**; entering takes `F` followed by `Enter` (menu.c's hotkey semantics).
2. Always wait for `commandQueue.idle` before navigation assertions: with a fetch in flight, `_requestEnd`/`_requestHome` are **foreground first**
   (dropping unsent prefetches and shortening the in-flight one with `expedite`, see easy-reading-list.md invariant 18); only
   `hasKind('brd-jump-')` (deduplicating repeated presses) really skips queueing, so the wait is for "the previous number jump to land"; without it a test may pass on "nothing happened".

**Offline cassettes record only a category board subcategory**: guest has no favorites (§1), and favorites are a personal preference list that must not enter the repo.
A category subcategory is public site content reachable as guest, and its footer variant differs from favorites only by one phrase, so coverage of the rendering and scrolling paths is equivalent.
Details in `docs/offline-replay-testing.md`.

## 7. Not done (explicitly out of scope)

- All boards: tens of thousands of rows; how evict with `MAX_LIST_ROWS=300` feels is unverified. Popular boards do not engage in the old version, and in the new version they engage because they cannot be told apart from a category subcategory (§1).
- Cross-list resume: only "enter board → leave board" goes through `suspended` and reuses the buffer; `y`/`c`/`/` and entering or leaving categories all replace the whole number space and re-seed.
  Doing it would need a fingerprint that can tell "the same list" (footer variant + row 1 + an estimate of brdnum).
- Background prefetch is currently capped at a hard-coded 3 pages (`FILL_MAX_PAGES`), and shares
  `easyReadingListPrefetchCount` with the article list as the target row count.
